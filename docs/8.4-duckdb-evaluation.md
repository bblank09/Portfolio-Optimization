# Checklist 8.4 — Evaluate migrating to DuckDB

**Decision: do not migrate now.** Revisit once the fund universe pull (8.8)
has actually landed and `daily_nav.parquet` is measured, not projected.

## Why this needed evaluating

Phase 8.8 will grow `daily_nav.parquet` from 12 funds (~30k rows, 2.3MB) to
the full SEC mutual fund universe (likely 1000+ funds, ~10 years of daily
NAV each) — plausibly hundreds of MB to a few GB. 8.3 already added
`filters=[("proj_id","in",proj_ids)]` to `pd.read_parquet()` so pyarrow
prunes row groups before rows reach pandas. The question is whether that's
enough, or whether the query layer itself needs to become DuckDB.

## What DuckDB actually adds over pandas+pyarrow

1. **Same pushdown, plus out-of-core.** DuckDB supports the identical
   filter/projection pushdown pyarrow already does for parquet (row-group
   skipping via zonemaps) — no advantage there, 8.3 already captured it. Its
   real edge is a genuine out-of-core engine: streaming execution with
   automatic spill-to-disk for datasets larger than RAM, which pandas cannot
   do (pandas always materializes the full result in memory).
   ([DuckDB Parquet docs](https://duckdb.org/docs/current/data/parquet/overview),
   [DuckDB memory management](https://duckdb.org/2024/07/09/memory-management))

2. **No official DuckDB-vs-pyarrow-filtered-scan benchmark exists.**
   Third-party (non-peer-reviewed) tests show real gaps favoring DuckDB on
   filtered scans, but nothing authoritative for our exact access pattern.
   [unverified rigor] ([Medium writeup](https://medium.com/@hadiyolworld007/the-duckdb-pushdown-that-beat-pandas-by-10-852c2549f084))

3. **Low integration risk if adopted.** DuckDB is designed as a query layer
   that hands off to pandas at the end (`duckdb.sql(...).df()`), not a
   pandas replacement. The existing pandas/numpy calculation engine
   (Sharpe, drawdown, correlation, etc.) would not need to change — only
   `load_nav_panel()`'s read path would.
   ([DuckDB Python API](https://duckdb.org/docs/current/clients/python/overview),
   [Export to Pandas guide](https://duckdb.org/docs/current/guides/python/export_pandas))

4. **No fixed size threshold, but our access pattern is the deciding
   factor, not file size.** DuckDB's advantage grows with file size and
   filter selectivity, but more importantly: our query shape is "give me
   these 1-20 proj_ids out of ~1000+" — a highly selective point-style
   filter, not a whole-dataset aggregation.
   ([Orchestra: querying data larger than RAM](https://www.getorchestra.io/guides/can-duckdb-query-data-larger-than-ram))

5. **DuckDB's sweet spot is OLAP aggregation, not selective point lookups.**
   DuckDB is explicitly an OLAP engine (columnar, vectorized, batch
   analytical scans), not built for OLTP-style single-key lookups — one
   benchmark found an 8x per-operation gap for point lookups vs. row-oriented
   stores, widening to 35x under concurrency. Our "N proj_ids out of many"
   pattern sits in DuckDB's reasonable-but-not-ideal middle ground, not its
   true sweet spot (whole-dataset aggregation across all funds at once).
   ([MotherDuck: what is DuckDB](https://motherduck.com/learn/what-is-duckdb/),
   [ClickHouse: OLTP vs OLAP](https://clickhouse.com/resources/engineering/oltp-vs-olap))

## Verdict

- 8.3's row-group filter pushdown already solves the acute "RAM explodes on
  every request" risk for our actual access pattern (a handful of funds
  per backtest request, out of the full universe).
- DuckDB would add a new dependency and a rewrite of the read path for a
  benefit that's real at scale but unproven at our specific size and
  access pattern, and there's no primary-source benchmark for exactly our
  case ("N proj_ids out of thousands").
- The one workload where DuckDB would clearly help — a whole-universe
  aggregate query (e.g. "compute something across every fund at once") —
  does not currently exist in this app. Every request scopes to a small,
  user-selected fund list.

## Revisit trigger

Re-evaluate this decision if, after 8.8 lands and the real parquet file
size/row count is measured, any of the following become true:
- `daily_nav.parquet` exceeds ~500MB-1GB (the point where out-of-core
  safety stops being theoretical), or
- A feature needs a whole-universe aggregate scan (e.g. "screen all funds
  by some criterion"), which is DuckDB's actual sweet spot, or
- `load_nav_panel()` is observed to be a real latency/memory bottleneck in
  production, not just a projected one.

If none of these hold, the pyarrow filter pushdown from 8.3 remains
sufficient and DuckDB migration should stay deferred.
