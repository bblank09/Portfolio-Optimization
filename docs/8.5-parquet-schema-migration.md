# Checklist 8.5 — Parquet schema migration strategy

## The problem this solves

The SEC NAV cache (`data/sec/normalized/*.parquet`) is committed straight to
git and read by both the running app and CI. When a future change needs a
new field — the concrete case right now is checklist 8.8 (pulling the full
SEC fund universe) wanting `fund_status` and `cancel_date` on
`fund_classes.parquet` so a later survivorship-bias audit (checklist 3.2)
can tell which funds have since closed/merged — the committed parquet
files don't have that column yet. Re-downloading everything from SEC just
to add one column would be slow, hit rate limits, and risk 8.7's retry
budget for no reason.

## Strategy: additive-only migration, never in-place rewrite of meaning

`backend/app/sec/cache.py::migrate_schema(name, defaults)` is the one
function that changes a cached parquet's schema. Its rules, by design:

1. **Only adds columns, never renames or drops one.** A consumer written
   against the old schema still works after migration — it just doesn't see
   the new column, which is fine because nothing depended on it yet.
2. **Never overwrites an existing value.** If a column already exists
   (even from a partial prior migration), its data is left exactly as-is.
3. **Idempotent.** Running the same migration twice is a no-op the second
   time — safe to put in a script that gets re-run.
4. **Fails loudly on a genuinely missing dataset** (`FileNotFoundError`)
   rather than silently creating an empty file with the new schema, since a
   missing cache is a setup problem, not something to paper over.

This mirrors how the rest of the pipeline already treats schema change:
`normalizers.py::normalize_fund_class_record()` already returns
`fund_status`/`proj_name_th`/`proj_name_en` from the SEC API response —
`sec_build_mvp_universe.py` just doesn't currently choose to persist them.
Adding them is a pure schema *addition*, not a breaking change to anything
downstream (`load_nav_panel()`, the backtest engine, and the frontend never
read `fund_classes.parquet` directly for anything beyond what they already
use).

## What this deliberately does not do

- **No `schema_version` field.** With an additive-only strategy, "what
  schema does this file have" is answered by `df.columns` itself — a
  separate version counter would just be another thing to keep in sync and
  another way for the two to drift. If a future migration ever needs to be
  non-additive (a real type change, not just a new column), that is the
  point to introduce versioning, not before.
- **No automatic migration on app startup.** Migrations are a deliberate,
  reviewable step (`scripts/sec_migrate_schema.py`, this PR), not something
  that silently mutates the committed cache when someone happens to boot
  the app. That would make "what changed and why" invisible in git history.
- **No atomic temp-file-then-rename write.** `migrate_schema()` writes
  directly to the target path, same as `write_parquet()` already does
  elsewhere in this file. Genuine concurrent-write safety is checklist 5.5;
  bundling it here would be scope creep for a Low-complexity item.

## How to add a new column in practice

1. Add `{"new_column": default_value}` to the relevant entry in
   `TARGET_SCHEMAS` in `scripts/sec_migrate_schema.py`.
2. Run `python scripts/sec_migrate_schema.py` — it prints which columns
   were actually added per file (or `"already up to date"`).
3. Commit the migrated parquet alongside the code that now reads/writes the
   new column, in the same PR — so the schema change and its consumer land
   together, not as a silent prerequisite commit.

## Worked example already wired up

`scripts/sec_migrate_schema.py` currently migrates `fund_classes.parquet`
to add `fund_status` (empty string default) and `cancel_date` (`None`
default) — the two fields checklist 8.8's full-universe pull and checklist
3.2's survivorship-bias audit will need. It has not been run against the
committed cache yet because nothing downstream reads those columns until
8.8 actually lands; running it now would just add two unused columns.
